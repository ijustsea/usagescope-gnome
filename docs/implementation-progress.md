## Fresh boundary review and recovery hardening — v0.2.1

The user requested a fresh security review plus a combined Korean architecture/technology-choice learning document. The following changes are based on owned temporary fixtures, code inspection and actual execution; no external target was attacked.

- Conditional P1, directory ancestors: a 0700 config under a nonsticky 0777 ancestor was accepted, permitting another user to replace its name and the referenced wrapper. Config/runtime directory validation now checks the entire owner/mode chain, rejects symlinks, and only exempts root-owned sticky shared directories. Independent controlled fixtures reject 0770/0777/user-owned01777 ancestors and accept a safe directory under root-owned sticky `/tmp`.
- P2, publication contention: near-full concurrent immutable snapshot writes could exceed the inventory limit after commit and strand the directory. The failing invocation now withdraws only its own new commit on postcommit inventory/retention failure. Independent seeded32snapshots+16caches/32writers runs changed from persistent65–78entries to48entries and a successful next normal export (4/4 runs); the committed regression also checks postcommit failure rollback.
- P2, restore concurrent edits: an explicitly injected check/use interleaving reproduced deletion of a concurrent settings edit when the original file was absent. Restore now captures the inode before validation, publishes originals exclusively, preserves edited settings and the live wrapper on conflict, and retains private `.usagescope-recovery-*` archives (cap16) even on success. Tests cover edits retaining statusLine.command, late writes through held FDs, exact original bytes/mode, repeat apply/restore and full archive refusal. This fixture establishes a correctness race, not an independently observed foreign-user exploit.
- App Server input bounds: per-frame limits alone did not bound a connection's cumulative input or many small messages. Added4MiB stdout/256message budgets, verified with real GJS pipes carrying small-message floods and multiple valid large frames.
- Normal Codex completion: replaced immediate termination after successful quota reads with stdin EOF, up to2seconds exit waiting and owned-child fallback termination. Disable/error still detach and terminate immediately. The wait callback now consumes wait_finish and the read loops close their streams. EOF marker, child reaping and uncooperative-child fixtures cover both paths.

## Lighter polling: idle pause, Codex plugin sync off, no blanking on account/updated — v0.4.3

The user asked for minimal CPU and resource use, and for no interference with their existing workflow or browser. The measurements came first. UsageScope itself is negligible. The cost is the official CLI started for each read: Claude about 0.45 CPU-seconds and Codex about 0.3. On this machine `org.gnome.desktop.session idle-delay` is 0, so the screen never blanks or locks and reads continued while the user was away. GNOME 51 disables extensions without `unlock-dialog` in `session-modes` on lock (`_extensionSupportsSessionMode` in the installed libshell), so a locked screen already stops reads.

- **Idle pause**: Mutter's core idle monitor pauses both controllers after 5 minutes without input. The watch is uninhibitable, so video playback does not keep reads running. A pause keeps the last view and cancels the next scheduled read. The first input resumes with one immediate read and the normal interval. Resume ignores any failure backoff, so a period idle for 5 minutes or more can cost at most one extra read. A provider restarted while idle (for example a gsettings change) is paused before start, so it does not read until input. Disable removes both watches. Verified in headless GNOME 51 with a temporary 3 s threshold: after 7.7 s idle both controllers were paused with no timers; a virtual pointer motion resumed both with an immediate read and new timers. Unit tests use a fake monitor, and GJS tests cover real pause/resume on both controllers.
- **Codex plugin sync**: Codex 0.171.0 app-server ran plugin/marketplace sync on every read and sometimes staged a marketplace checkout under `~/.codex/.tmp`. The quota process now starts with `-c features.plugins=false -c features.remote_plugin=false`. These are process-only overrides; `config.toml` was unchanged, and unlike `--disable`, `-c` ignores unknown feature names, so a future removal cannot break reads. Measured through the production GJS path, three alternating runs each: total CPU went from 0.38–0.39 s to 0.27–0.29 s (about 28% less), with no marketplace checkout (it appeared in 1 of 3 runs without the overrides). State DB and model-cache writes (3–8 files) still occur either way as Codex startup behavior, so an earlier interim statement of "zero file writes" was wrong and is corrected here.
- **account/updated bug**: Real Codex emits `account/updated` during many ordinary reads. The controller cleared its state on it, so the card and panel blanked (`loading → waiting(empty) → loading → ready`), and `LowQuotaAlerts.observe` reset the baseline on the empty view. The next sample then counted as a first sample, so ChatGPT's 30% alert could fail to fire. The controller now discards the in-flight response and redoes the read on the same process while keeping the last quota. After a real account switch, the old quota stays visible only until the redone read (about 0.5 s, status `loading`). Its `accountId`, when Codex reports one, starts a new alert baseline. Upstream describes this notification as routing discovery for the same authenticated owner. A new GJS regression test failed before the fix with the observed sequence and passes after it. Real Codex now shows `loading → loading → ready`.

Verification: `npm run check` passes 47 Node tests and all 3 GJS suites. Packaged headless GNOME checks pass at 1280x720 and 1024x480, including disable/re-enable with idle watches registered. Five scratch-copy mutations were caught: the Codex overrides, both pause guards, pausing a provider restarted while idle, and watch removal on disable. An independent review found no blocking issue. Its findings were addressed: the resume tests now assert that a read starts immediately (a reviewer mutant had passed them); a provider started while idle no longer reads; the watch ignores inhibitors; and comments no longer overstate the role of `accountId`.

## Claude usage matches the website: stop blocking the usage fetch — v0.4.4

After 0.4.3 was installed, the Claude card showed `한도 정보 미제공` while claude.ai showed Team 71%/12%. Earlier it had shown 16%/3% against the website's 48%/8%. The cause was UsageScope's own `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, added in 0.4.0.

- **Evidence**: In Claude Code 2.1.323, `get_usage` → `r7t` → `R()` answers from the shared `cachedUsageUtilization` in `~/.claude.json` when it is under 60 s old (`_t = 60000`). After a failed or skipped server read, it answers from that cache when it is up to an hour old (`Tn = 3600000`, status `seeded`), and otherwise returns `rate_limits: null`. With the variable set, every `get_usage` answered in 0.00 s with no network connection, from whatever another Claude process (here, the interactive Claude Code session) had cached. After `/login`, the cache was dropped for the new account, so the answer was null. Without the variable, the same request took 0.37–0.39 s, returned a new `resets_at` fraction (a real server read) and gave 74–77%, matching the website within minutes.
- **Fix**: The quota process sets `DISABLE_TELEMETRY=1` and `DISABLE_ERROR_REPORTING=1` instead, and unsets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` even when the user sets it globally. Single 61-second-spaced runs: no variables took 0.90 CPU-s with Anthropic and Datadog connections. Telemetry and error reporting off took 0.66 CPU-s with only the Anthropic connection and still read the server. The blocking variable took 0.38 CPU-s with no connection and no fresh read. Through the production GJS path, the shared cache went from 200 s old to 0 s old, with 77%.
- **Corrections to earlier sections**: The 0.4.0 "Environment impact" figures (0.32–0.41 s, Datadog removed, no remote-settings writes) measured a read that never asked the server, so they are not a saving. The 0.4.2 diagnosis that CLI and website disagree upstream was wrong for this account: the mismatch was UsageScope serving a stale cache. A cache up to 60 s old, plus the poll interval, can still lag the website slightly.

Verification: `npm run check` passes. The fake CLI now rejects the blocking variable and requires the telemetry and error-reporting overrides, so the GJS suite and test:shell fail if either regresses.
